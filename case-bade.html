Backend Architecture Discovery Engine

An evidence-driven discovery engine that auto-generates a stakeholder-friendly trust-boundary diagram on every scan — by correlating service inventory, team-declared dependencies, cloud infrastructure and code, so threat modelling and reviews start from facts, not stale hand-drawn docs.

The challenge

A large mobile backend platform — the single path from the mobile apps into dozens of downstream booking, payments, identity and content systems — had grown so large that no single engineer could describe its architecture from memory. Teams kept accurate data in their own tools (observability for alerting, a service catalog for onboarding, cloud tags for billing), but none of those, alone, was the architecture diagram the security team needed.

  • Threat modelling without a diagram is a wish STRIDE-per-trust-boundary modelling needs a current L1–L4 diagram as input. Hand-maintained diagrams drifted within weeks — in one 90-minute workshop, 30 minutes were lost arguing whether a service still existed.
  • Onboarding was tribal knowledge A new engineer needed roughly a quarter to answer "if I change payments, who else is affected?" The answer existed implicitly across three tools, but no one had assembled it into a navigable view.
  • Cross-team impact was invisible A shadow dependency — a runtime call not declared in the service catalog — caused a production incident during a migration that hand-maintained docs could never have caught.
The real problem wasn't "we need a better diagramming tool." It was: we need a diagram that is a function of the systems, not a human's memory of them.

The approach — design principles I set

  • Read what teams already maintain No team should maintain a new data source whose only consumer is this tool. Observability, service catalog, cloud and CI are all kept current for their own reasons — so their accuracy is self-enforcing.
  • Evidence must be distinguishable A team-declared dependency is not the same as an observed runtime call. The engine preserves that distinction end to end, with a typed evidence model and a confidence score per claim.
  • Deterministic first, AI second Correlation is reproducible and reviewable. AI (Amazon Bedrock) helps only with ambiguous name matching and grouping — never as the sole basis for an architecture claim, and it can never promote an edge to "verified".
  • Catalog-first for structure When sources disagree, the team-declared catalog wins. Runtime calls the catalog doesn't declare become shadow candidates for review — never silent additions.
  • Adopt via one line of CI The ceiling for adoption is the first team that gives up because setup is complicated. One include block plus two variables — or no adoption.
  • Read-only, least privilege Every source is consumed read-only. Cloud access is via CI OIDC and IAM role assumption — no long-lived keys. Nothing writes back.

How it works

Four pluggable collectors each produce typed evidence; a deterministic correlation engine merges them; an optional AI layer reconciles names; and exporters render three artefact sets on every scan.

Observability (runtime) Service catalog (declared) Cloud (infra) CI / code (call-sites)
↓
Typed evidence + confidence → Deterministic correlation → AI name reconciliation (advisory)
↓
Trust-boundary diagram (L1–L4) Per-service dependency graph Shadow-dependencies report

Typed evidence model

Each collector emits assertions tagged with an evidence kind and a calibrated confidence. An edge seen by both the catalog and runtime gets a corroboration bonus; an edge seen only at runtime is a shadow candidate.

RUNTIMEObserved service-to-service calls (observability API)
CATALOGTeam-declared dependencies (Backstage API)
INFRA_CONFIGCloud resources read-only (ECS, DynamoDB, SNS, cache)
CODE_DEFINEDHTTP client call-sites via Tree-sitter source scan
AI_INFERREDBedrock name/grouping hints — low weight, never corroborating on its own

Engineering highlights

  • Python 3.12, packaged as a Docker image and a reusable GitLab CI template — adopters add one include block and two masked variables.
  • Deterministic-first grouping with a curated-layout override, so auto-generated diagrams still match each team's mental model.
  • Prompt-injection defence: all external text (service descriptions, catalog metadata, source files) is wrapped as untrusted data in AI prompts.
  • Soft-fail design: missing credentials or partial source outages degrade gracefully rather than breaking the pipeline.
  • 108 tests, lint/format clean, with CI jobs for collector smoke tests, end-to-end scan validation and AI connectivity.

Outcomes & lessons

  • One scan mapped 76+ services, correlated 286 declared edges with 4,208 runtime calls, and surfaced 174 double-corroborated dependencies plus a reviewable set of shadow dependencies.
  • Zero diagram drift — the output regenerates on every pipeline run and now feeds the threat-modelling workflow directly.
  • Treating the team-declared catalog as authoritative was the highest-leverage decision — it kept runtime noise from drowning the signal (a naive version would have shown 4,208 "edges", most irrelevant).
  • Live data beats committed snapshots: switching from a committed CSV to the live observability API was the single change that moved it from "demo" to "production tool".
  • The first external team was onboarded via the CI template with a green end-to-end pipeline — proving the one-line adoption model.

Case Study • Security Standards & Governance

Security Standards for Modular Architecture (MWA & MSA)

I act as the security reviewer for the standards, guidelines and best practices of TUI's Modular Architecture, and I write its security checklists, reference patterns and runbooks. Engineers and teams across TUI build on this guidance, and I keep it current as technology, tools and threats change.

Role
Security reviewer for all Modular Architecture standards, guidelines and best practices; author of the security checklists, patterns and runbooks
Status
Live and continuously maintained; used by around 800 engineers and teams across TUI
Scope
Modular Web Architecture (MWA) and Modular Service Architecture (MSA)

Why it was needed

TUI moved to a modular platform where many independent teams build and release micro frontends and services on shared infrastructure. That is good for speed and hard for security.

  • Security does not scale by review A small security team cannot review every micro frontend and service by hand. Without a written baseline, each team decides alone what “secure enough” means.
  • Inconsistent decisions Teams interpreted the same topics differently: where secrets live, what an error response may reveal, what may go into logs, how strict a Content Security Policy must be.
  • One weakness is repeated across teams Shared boilerplates, pipeline templates and ingress mean one weak pattern, or one compromised template or dependency, spreads to many teams at once.
  • Guidance goes stale Frameworks, cloud services and attack techniques change. A standard written once and never revisited quietly becomes wrong.
Security in a modular platform is a property of the platform, not of each team's memory.

What I do

Security review of every document Every standard, guideline and best practice in Modular Architecture, on the web (MWA) and service (MSA) side, gets a security review. Requirements are built in at the source instead of bolted on in team reviews.
MFE Security Checklist The baseline every micro frontend needs: secrets, input validation at the BFF, error handling, log hygiene, dependencies, the security pipeline, GraphQL protection, abuse prevention, and authentication and authorisation (access tokens never reach the browser).
Supply-chain checklist Exact version pinning and committed lockfiles, CI templates referenced by immutable version, internal modules from an internal registry, and releases only through CI. It points to existing central standards and adds only what is missing.
Reference security patterns Seven worked patterns teams can copy: API security headers, CSP, Apigee X, Cognito and API Gateway in Terraform, TLS, and GraphQL / OWASP API Top 10.
Self-service runbooks Seven runbooks so teams can fix common findings without waiting for the security team. A few items were promoted into the TUI Technology Standards.
Versioned and announced Each document is versioned with a changelog and a clear status, so teams see what changed and when. Upcoming enforcement, for example mandatory lockfiles, is announced in advance.

Design principles

  • Every item is provable A checkbox is either confirmed or empty. There are no “continuously ensure” items.
  • Secure by default, not by memory What the platform can enforce (encryption defaults, query protection, HTTPS and WAF at the edge, the PreFlight scan in every pipeline) lives in the boilerplate and the edge. Teams own only the rest.
  • Defence in depth Design-time threat modelling, automated scanning in every pipeline and cloud posture monitoring work together, so no single control carries all the risk.
  • Do not restate what is already mandated Link to the central standards and add only the gap, so guidance stays short enough to be used.
  • Right-sized by archetype Separate sections for public and protected micro frontends, so teams do only what applies to them.

Kept current as technology changes

Guidance is reviewed and updated whenever one of these happens:

  • A technology change — a new framework, runtime or cloud service version changes what “secure” looks like.
  • A tool change — when scanners, pipelines or platform tooling change, the guidance and checklists change with them.
  • An incident — lessons from a real incident or a recurring finding go back into the standard.
  • A periodic cycle — a scheduled re-review so guidance does not drift even when nothing obvious has changed.

The result

  • A common definition of “secure enough” for the engineers and teams across TUI, usable from day one without a meeting.
  • Less review load — the pipeline and the checklist catch the common findings first, so security reviews can focus on design risk.
  • Consistent security across web and services, because one reviewer sees every standard on both sides.
  • Visible, auditable posture — binary checklist items let a review or a periodic check confirm the state with evidence.
  • Standards that do not rot — versioned, changelogged and re-reviewed when technology, tools or threats change.
Bottom line: the platform carries what it can, the checklists carry the rest, and a single security reviewer keeps both current.
